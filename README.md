# BillPay

Сервис напоминаний о регулярных платежах: аренда, подписки, серверы и прочие ежемесячные расходы. Решение кейса «Invoice Keeper» от aéza.

Администратор заводит платежи и пользователей. Пользователи видят общий список, отмечают оплату и указывают фактическую дату. За 3 дня до срока бот пишет в Telegram-чат. Дополнительно можно включить письма на почту и вебхук.

Рабочая версия: https://billpay.outskip.space

Код: https://github.com/xeon-cloud/billpay (зеркало на SourceCraft: https://sourcecraft.dev/xeonvsd/billpay)

## Что нужно для запуска

- Docker с Docker Compose v2 (команда `docker compose`, не `docker-compose`).
- Свободный порт 3000 на машине. Если занят, порт меняется в `.env`.
- Для напоминаний в Telegram: токен бота от @BotFather и группа, куда этот бот добавлен.

Node.js ставить не нужно, всё собирается внутри контейнера. Node 20 понадобится только для тестов и запуска без Docker (об этом ниже).

## Быстрый запуск

```bash
git clone https://github.com/xeon-cloud/billpay.git
cd billpay
cp .env.example .env
```

Откройте `.env` в редакторе и замените заглушки `change-me`. Без этого приложение не стартует, это сделано специально:

- `POSTGRES_PASSWORD` — любой пароль для базы.
- `DATABASE_URL` — поменяйте в нём пароль на тот же. В Docker эта строка не используется, она нужна для запуска без Docker.
- `SESSION_SECRET` — случайная строка не короче 32 символов.
- `ADMIN_PASSWORD` — пароль администратора, от 8 символов. Простые вроде `admin123` или `password` не пройдут.

Сгенерировать секрет можно так:

```bash
openssl rand -hex 32
```

Дальше:

```bash
docker compose up -d --build
```

Первая сборка занимает минуту-две. Поднимутся три контейнера: `db` (PostgreSQL 16), `app` (веб-панель и API) и `bot` (проверка сроков и отправка напоминаний). Миграции базы применяются сами при старте.

Проверить, что всё живо:

```bash
docker compose ps
curl http://localhost:3000/healthz
```

Должно вернуться `{"status":"ok","db":"ok"}`.

Панель: http://localhost:3000/login. Вход под администратором: логин `admin` (значение `ADMIN_LOGIN`) и пароль, который вы указали в `ADMIN_PASSWORD`.

Логи, если что-то пошло не так:

```bash
docker compose logs -f app bot
```

Если бот пишет `бот ждёт TELEGRAM_BOT_TOKEN и TELEGRAM_CHAT_ID`, значит Telegram ещё не настроен. Панель при этом работает.

## Учётные записи

Администратор один, он задаётся только в `.env` (`ADMIN_LOGIN`, `ADMIN_PASSWORD`, `ADMIN_NAME`). При каждом старте приложение синхронизирует его с `.env`. Через панель и API его нельзя изменить или удалить, и второго администратора создать тоже нельзя.

Обычных пользователей администратор создаёт в разделе «Пользователи» (http://localhost:3000/app/admin) или через `POST /api/v1/users`. Готовых демо-пользователей в базе нет, их создают тестовые данные из следующего раздела.

Что может пользователь: смотреть общий список платежей, ставить и снимать отметку «Оплачено», указывать и исправлять фактическую дату оплаты, прикладывать чек или ссылку. Добавлять и удалять платежи, управлять пользователями и смотреть журнал он не может. Это проверяется на сервере, через API тоже вернётся 403.

## Тестовые данные

База после запуска пустая. Ниже команды, которые создают три платежа из кейса (аренда в рублях, сервер в долларах, подписка в евро) и пользователя `user` с паролем `user-pass`. Данные можно завести и руками через панель, результат тот же.

Даты стоят под 25.10.2026. Если запускаете в другой день, сдвиньте их: аренда через 1–3 дня от сегодня, чтобы сразу пришло напоминание, сервер на несколько дней назад, чтобы показать просрочку, подписка в следующем месяце.

```bash
B=http://localhost:3000
ADMIN_PASSWORD='<пароль администратора из .env>'

curl -s -c admin.txt -H 'Content-Type: application/json' \
  -d "{\"login\":\"admin\",\"password\":\"$ADMIN_PASSWORD\"}" $B/api/v1/auth/login

curl -s -b admin.txt -H 'Content-Type: application/json' \
  -d '{"name":"Аренда офиса","amount":85000,"currency":"RUB","next_date":"2026-10-27"}' \
  $B/api/v1/recurring-payments

curl -s -b admin.txt -H 'Content-Type: application/json' \
  -d '{"name":"Сервер","amount":49.9,"currency":"USD","next_date":"2026-10-20"}' \
  $B/api/v1/recurring-payments

curl -s -b admin.txt -H 'Content-Type: application/json' \
  -d '{"name":"Подписка на дизайн-сервис","amount":15,"currency":"EUR","next_date":"2026-11-05"}' \
  $B/api/v1/recurring-payments

curl -s -b admin.txt -H 'Content-Type: application/json' \
  -d '{"login":"user","password":"user-pass","name":"Иван"}' \
  $B/api/v1/users
```

После этого можно зайти как `user` / `user-pass` и отметить оплату. Файлы `admin.txt` с cookie потом удалите.

Начать с чистой базы (останется только администратор из `.env`):

```bash
docker compose exec app node src/reset.js --yes
```

## Telegram

1. Создайте бота у @BotFather и скопируйте токен.
2. Создайте группу (или возьмите готовую) и добавьте туда бота.
3. Узнайте id чата. Если бот из BillPay уже запущен, остановите его на время (`docker compose stop bot`), иначе он заберёт обновления себе. Потом напишите в группе любое сообщение, например `/start@имя_бота`, и выполните:

   ```bash
   curl -s 'https://api.telegram.org/bot<токен бота>/getUpdates?allowed_updates=%5B%22message%22%2C%22my_chat_member%22%5D'
   ```

   В ответе ищите `"chat":{"id":-100...`. У групп id отрицательный, минус тоже нужен.
4. Впишите в `.env`:

   ```
   TELEGRAM_BOT_TOKEN=<токен бота>
   TELEGRAM_CHAT_ID=<id чата>
   TELEGRAM_CHAT=Финансы
   ```

   `TELEGRAM_CHAT` — просто название чата, которое показывается в интерфейсе.
5. Перезапустите контейнеры, чтобы они перечитали `.env`:

   ```bash
   docker compose up -d
   ```

Как это работает. Бот раз в минуту смотрит неоплаченные периоды со сроком в ближайшие `REMIND_DAYS_BEFORE` дней (по умолчанию 3) и уже просроченные. По каждому отправляется одно сообщение: название, сумма, валюта и дата. Каждая отправка записывается в базу, поэтому повторная проверка или перезапуск дубль не создают. Если платёж добавили позже чем за 3 дня до срока, сообщение придёт в течение минуты. Оплаченный период и удалённый платёж напоминаний не дают.

Под сообщением есть кнопка «Оплачено». Нажатие отмечает период оплаченным сегодняшним числом, сообщение обновляется.

Проверить быстро: добавьте платёж со сроком через 1–2 дня и подождите минуту. В `docker compose logs bot` появится строка `напоминание отправлено`.

## Почта

Письма уходят тем пользователям, у которых указан email (в профиле или в карточке пользователя у администратора). Нужны как минимум `SMTP_HOST` и `SMTP_FROM`:

```
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USER=<логин>
SMTP_PASS=<пароль>
SMTP_FROM=BillPay <billpay@example.com>
APP_URL=http://localhost:3000
```

Порт 465 работает через SSL, остальные через STARTTLS. Если `SMTP_PORT` пустой, берётся 587. `APP_URL` нужен для ссылки на платёж в письме.

Чтобы посмотреть письма без настоящего SMTP, в compose есть Mailpit:

```
SMTP_HOST=mailpit
SMTP_PORT=1025
SMTP_FROM=BillPay <billpay@example.com>
```

```bash
docker compose --profile mailpit up -d
```

Все письма будут видны на http://localhost:8025 (порт меняется через `MAILPIT_PORT`). Наружу они не уходят.

## Вебхук

Если задать `WEBHOOK_URL`, на этот адрес уходит POST на каждое напоминание. Засчитывается только ответ 2xx, таймаут 10 секунд, при ошибке бот повторит попытку через минуту.

```json
{
  "event": "payment.reminder",
  "delivery_id": "12",
  "sent_at": "2026-10-25T08:56:13.221Z",
  "data": {
    "occurrence_id": 1,
    "payment_id": 1,
    "name": "Аренда офиса",
    "amount": 85000,
    "currency": "RUB",
    "due_date": "2026-10-27",
    "status": "unpaid",
    "days_left": 2,
    "url": "http://localhost:3000/app/calendar?date=2026-10-27"
  }
}
```

`status` бывает `unpaid` или `overdue`, `url` равен `null`, если не задан `APP_URL`. В заголовках приходят `X-BillPay-Event` и `X-BillPay-Delivery`.

`WEBHOOK_SECRET` необязателен. Если он задан, добавляется заголовок `X-BillPay-Signature: sha256=<hex>`, это HMAC-SHA256 от тела запроса. Получатель считает такой же HMAC своим секретом и сравнивает, так он понимает, что запрос пришёл от BillPay и тело не меняли.

## Переменные окружения

Полный список лежит в `.env.example`, секретов там нет. Пустая переменная означает значение по умолчанию.

База:

- `POSTGRES_USER`, `POSTGRES_DB` — по умолчанию `billpay`.
- `POSTGRES_PASSWORD` — обязательно.
- `DATABASE_URL` — строка подключения для запуска без Docker. В контейнерах не используется, там приложение подключается к сервису `db`.
- `DATABASE_SSL` — `true`, если база требует SSL. По умолчанию `false`.
- `DB_POOL_MAX` — размер пула соединений, по умолчанию 10.

Приложение:

- `PORT` — порт на хосте, по умолчанию 3000.
- `APP_BIND` — на каком адресе хоста слушать, по умолчанию `127.0.0.1`. Чтобы открыть панель другим машинам в сети, поставьте `0.0.0.0`.
- `TZ`, `APP_TIMEZONE` — часовой пояс, по умолчанию `Europe/Moscow`. Все сроки, «сегодня» и просрочки считаются в нём.
- `APP_URL` — публичный адрес панели, нужен для ссылок в письмах и вебхуке.

Сессии и вход:

- `SESSION_SECRET` — обязательно, от 32 символов.
- `SESSION_TTL_HOURS` — срок жизни сессии, по умолчанию 168 (неделя).
- `COOKIE_SECURE` — `true`, если панель открывается по HTTPS.
- `TRUST_PROXY` — сколько прокси перед приложением, по умолчанию 1.
- `LOGIN_RATE_MAX`, `LOGIN_RATE_WINDOW_MIN` — не больше 10 неудачных входов за 15 минут с одного адреса.
- `LOG_RETENTION_DAYS` — сколько дней хранить журнал, по умолчанию 180.

Администратор: `ADMIN_LOGIN` (по умолчанию `admin`), `ADMIN_PASSWORD` (обязательно), `ADMIN_NAME`.

Напоминания: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_CHAT`, `REMIND_DAYS_BEFORE` (по умолчанию 3), `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`, `WEBHOOK_URL`, `WEBHOOK_SECRET`. Всё это описано выше в своих разделах.

После правки `.env` выполните `docker compose up -d`, контейнеры пересоздадутся с новыми значениями.

## Как устроены платежи

У регулярного платежа есть название, сумма, валюта (RUB, USD или EUR), дата ближайшей оплаты и периодичность. Сейчас поддерживается только ежемесячная, этого требует кейс.

Каждый месяц это отдельный период со своим сроком и своей отметкой об оплате. Следующий период создаётся автоматически, прошлые остаются в истории. Если нужного числа в месяце нет (31 число в ноябре), срок переносится на последний день месяца.

Просрочка начинается со следующего дня после срока, оплата в сам день срока считается вовремя. Если исправить фактическую дату оплаты, просрочка пересчитается, сам срок не меняется. При снятии отметки дата оплаты очищается.

Удалённый платёж пропадает из списка и больше не напоминает, но его прошлые периоды и оплаты сохраняются.

Итоги считаются отдельно по каждой валюте, без конвертации.

## Что есть в панели

- `/app` — платежи за месяц: сумма, валюта, срок, статус, дата оплаты, сколько дней просрочки, итоги по валютам. Поиск и фильтры по статусу и валюте.
- `/app/calendar` — календарь оплат и итоги на выбранную дату.
- `/app/admin` — пользователи и платежи (только администратор).
- `/app/logs` — журнал входов и действий (только администратор). Видно, кто входил, кто создал или удалил платёж, кто отметил оплату, в том числе кнопкой в Telegram.
- К оплаченному периоду можно приложить чек: PDF, JPG или PNG до 10 МБ, либо ссылку. Если снять отметку об оплате, чек остаётся.

Без входа страницы перекидывают на `/login`, а API отвечает 401.

## API и Swagger

Все эндпоинты начинаются с `/api/v1`.

- Swagger UI: http://localhost:3000/api/v1/docs
- Спецификация OpenAPI: `docs/openapi.yaml` в репозитории, она же отдаётся по `/api/v1/openapi.yaml` и `/api/v1/openapi.json`.

Авторизация через `POST /api/v1/auth/login`. Ответ ставит cookie `billpay_session` и возвращает `access_token`, который можно передавать в заголовке `Authorization: Bearer <токен>`. В Swagger достаточно выполнить login, дальше запросы пойдут с cookie.

Основные эндпоинты из кейса: `/auth/login`, `/auth/me`, `/auth/logout`, `/recurring-payments`, `/recurring-payments/{id}`, `/payment-occurrences`, `/payment-occurrences/{id}`, `/payments/summary`, `/users`, `/users/{id}`. Дополнительно: `/payment-occurrences/{id}/receipt` (чеки), `/logs/auth`, `/logs/actions`, `/logs/{id}` (журнал), `/meta`, `/health`.

Отметить оплату с исправленной датой:

```bash
curl -X PATCH -b user.txt -H 'Content-Type: application/json' \
  -d '{"is_paid":true,"paid_at":"2026-10-24"}' \
  http://localhost:3000/api/v1/payment-occurrences/1
```

Список за другой месяц: `GET /api/v1/payment-occurrences?month=2026-11`, итоги так же: `GET /api/v1/payments/summary?month=2026-11`.

## Данные и перезапуск

Данные PostgreSQL лежат в docker-томе `pgdata`, поэтому переживают `docker compose restart`, `down` и пересборку.

```bash
docker compose restart          # перезапуск
docker compose down             # остановить, данные остаются
docker compose down -v          # остановить и удалить базу целиком
```

## Тесты

Тесты интеграционные, им нужна живая база PostgreSQL. Каждый прогон создаёт свою временную схему и удаляет её в конце, рабочие данные не трогаются. Нужен Node.js 20.

```bash
npm ci
npm run db:up
TEST_DATABASE_URL=postgres://billpay:<пароль из POSTGRES_PASSWORD>@localhost:5432/billpay npm test
```

Если в `.env` уже исправлен `DATABASE_URL`, переменную `TEST_DATABASE_URL` можно не задавать, тесты возьмут его.

`npm run db:up` поднимает только контейнер с базой и открывает его на `127.0.0.1:5432`. Если порт 5432 занят локальным Postgres, задайте другой через `POSTGRES_PORT` перед командой и поправьте порт в строке подключения.

Сейчас 73 теста: права ролей, периоды и просрочки, напоминания без дублей, почта, вебхук, журнал и чеки. Те же тесты, проверка спецификации и запуск compose идут в GitHub Actions (`.github/workflows/ci.yml`).

## Запуск без Docker

Для разработки, жюри это не нужно.

```bash
npm ci
npm run db:up      # или свой PostgreSQL 16, тогда поправьте DATABASE_URL
npm run dev        # веб-панель с перезапуском при изменениях
npm run bot        # в соседнем терминале, напоминания
```

`npm run migrate` применяет миграции отдельно, хотя приложение и бот делают это сами при старте.

## На сервере

Для публичного адреса поставьте перед приложением reverse proxy с HTTPS (nginx, Caddy) на `127.0.0.1:3000`, в `.env` укажите `COOKIE_SECURE=true` и `APP_URL=https://ваш-домен`.

Если SMTP-сервер работает на самом хосте и слушает только 127.0.0.1, из обычной docker-сети бот до него не достучится. Для этого есть `docker-compose.host-smtp.yml`: бот переводится в сеть хоста, а база открывается на `127.0.0.1:${DB_HOST_PORT:-5432}`. Подключается так:

```bash
COMPOSE_FILE=docker-compose.yml:docker-compose.host-smtp.yml docker compose up -d
```

## Стек

Node.js 20, Express 5, PostgreSQL 16, Docker Compose. Вход по JWT в httpOnly cookie, пароли в bcrypt. Почта через Nodemailer. Миграции в папке `migrations`, применяются по порядку.
